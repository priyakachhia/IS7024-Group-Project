# Research: Save Analysis History

## Decision: Use Entity Framework Core with SQLite

- **Rationale**: The requested feature requires durable local storage without a separate database server. EF Core’s SQLite provider supports the required database lifecycle and keeps persistence code aligned with the existing .NET 10 application.
- **Alternatives considered**: MySQL was explicitly excluded; a JSON/file store would not satisfy the requested EF Core design or provide a relational schema for validated entries.

## Decision: Create the database at application startup

- **Rationale**: Calling `Database.EnsureCreatedAsync` during startup makes first-run setup automatic and avoids requiring a migration or database server for this small local feature.
- **Alternatives considered**: Manual database setup would violate the no-separate-server and automatic-first-run requirements. A migration pipeline is unnecessary for the initial simple schema and can be introduced later if schema evolution is needed.

## Decision: Keep persistence behind `IHistoryService`

- **Rationale**: The controller should depend on an application service rather than `HistoryDbContext`, allowing controller tests to use a fake and service tests to exercise SQLite behavior directly.
- **Alternatives considered**: Injecting the DbContext into the controller would couple the HTTP contract to persistence and make focused controller tests less direct.

## Decision: Use request/response DTOs with DataAnnotations

- **Rationale**: DTOs prevent the EF entity from becoming the public API contract and provide clear validation for required neighborhood, score ranges, non-negative counts, and date ordering. ASP.NET Core model binding can return a 400 response for invalid requests.
- **Alternatives considered**: Binding the entity directly would expose persistence concerns and make API validation less explicit.

## Decision: Use a client-side fetch script for both page interactions

- **Rationale**: The requirement explicitly calls for JavaScript `fetch` from Analyze and History. A dedicated `history.js` keeps the behavior out of Razor markup and lets the History page render a real table after loading JSON.
- **Alternatives considered**: Razor-only form posts or server-rendered History data would not meet the requested REST/fetch interaction.

## Decision: Use a full timestamp for ordering and display

- **Rationale**: Every save must be a distinct entry, and newest-first ordering requires a timestamp with sufficient precision. The saved timestamp is generated by the service rather than trusted from the client.
- **Alternatives considered**: Accepting a client-provided save time would allow inaccurate or tampered ordering data.
