# Research: Home Page Primary Action

## Decision 1: Keep the existing application platform and project shape

- **Decision**: Implement the feature in the existing .NET 10 ASP.NET Core Razor Pages project without changing the target framework or introducing a separate web application.
- **Rationale**: The repository already contains one Razor Pages web project targeting `net10.0`, and the feature is a single Home page flow. This minimizes migration and integration risk.
- **Alternatives considered**: Blazor or MVC were rejected because the existing application is Razor Pages and the feature does not require a new UI framework.

## Decision 2: Use a replaceable neighborhood repository boundary

- **Decision**: Define a repository interface for reading neighborhoods and register a seeded in-memory implementation through the existing dependency-injection container. Keep the Neighborhood entity limited to `Id` and `Name`.
- **Rationale**: The specification requires database-swappable data access while keeping the first implementation simple and deterministic. The interface gives tests a stable seam for seeded data, supported-neighborhood validation, and lookup by identifier; filtering remains browser-owned.
- **Alternatives considered**: Direct access to a collection in the PageModel was rejected because it couples page behavior to storage and makes replacement and focused tests harder. Adding a database was rejected as out of scope.

## Decision 3: Perform authoritative validation on the server

- **Decision**: Treat the posted business type and neighborhood selection as untrusted. Validate the business type against the four supported values and validate the submitted neighborhood against repository data before navigation. Preserve validation messages in the Razor Pages model state.
- **Rationale**: Client-side filtering improves interaction but cannot establish that submitted values are supported. Server validation prevents unsupported or stale values from reaching the Analyze URL.
- **Alternatives considered**: Client-only validation was rejected because it is bypassable and cannot reliably validate current repository data.

## Decision 4: Keep search interaction client-side while using the repository-loaded list

- **Decision**: Load the available neighborhoods for the Home page, then use the existing jQuery capability for trimmed, case-insensitive substring filtering and result selection. Editing the search input clears the hidden/posted selection and requires a new result selection.
- **Rationale**: The dataset is seeded and small for this feature, so a client-side filter keeps the interaction responsive without adding a search endpoint or unnecessary request lifecycle. The server still validates the final selection.
- **Alternatives considered**: A per-keystroke server search endpoint was rejected for the initial seeded dataset because it adds endpoint, loading, and failure-state complexity without user value.

## Decision 5: Use Razor Pages form navigation with framework URL generation

- **Decision**: Submit the validated form through the Home PageModel and redirect to the `/Analyze` page route with `neighborhood` and `businessType` query values generated by the framework so reserved characters are URL-encoded.
- **Rationale**: A server-side redirect provides one authoritative validation path and avoids hand-built query strings. The Analyze page itself remains unimplemented and is treated as a teammate-owned destination.
- **Alternatives considered**: Building the destination URL directly in browser script was rejected because it could bypass server validation and mishandle encoding.

## Decision 6: Add test coverage before production implementation

- **Decision**: Add a dedicated `net10.0` xUnit test project with candidate `Microsoft.NET.Test.Sdk` 17.14.x, `xunit` 2.9.x, `xunit.runner.visualstudio` 3.1.x, `Microsoft.AspNetCore.Mvc.Testing` 10.0.x, and `Microsoft.Playwright` 1.55.x targets. Write failing tests before implementation for seeded repository data and ID lookup, PageModel validation/navigation, browser-owned filtering and display/ID matching, keyboard/focus/status behavior, contrast states, and the 1366 × 768 and 320 CSS pixel constraints.
- **Rationale**: The current solution has no test project or test framework, so the plan must establish the test seam before feature code. These versions are planning candidates only; restore/build must succeed before compatibility is claimed. `WebApplicationFactory` will use the standard top-level `Program` test seam and requests will disable automatic redirects so tests inspect the `/Analyze` `Location` header without requiring that page. Playwright will use a fixture-managed local application process and install browser binaries through the generated install script after restore.
- **Alternatives considered**: Testing only through manual browsing was rejected because it cannot reliably protect server validation, navigation, or search behavior. A server-only test suite was rejected because it cannot verify client-side selection clearing, focus behavior, or the desktop viewport requirement.

## Decision 7: Keep visual work local to the Home page where possible

- **Decision**: Apply the compact dark navy header, white primary action panel, red Analyze button, layout, focus, and status styling in Home page-specific markup and stylesheet rules. Modify shared layout files only when required to expose the existing shared assets or avoid conflicting global behavior.
- **Rationale**: The specification explicitly asks to keep shared layout changes minimal and limits this work to the Home page primary action.
- **Alternatives considered**: Reworking the global navigation or shared layout theme was rejected because it expands scope and risks teammate work on other pages.
